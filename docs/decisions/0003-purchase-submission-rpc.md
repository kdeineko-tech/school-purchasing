# 0003. Подання закупівлі й рішення схвалювача — лише функціями бази

- Статус: прийнято
- Дата: 2026-10-25
- AC: AC-FRM-02, AC-FRM-04, AC-FRM-06, AC-FRM-07, AC-FRM-12, AC-FRM-13, AC-ORG-22, AC-ORG-23, AC-ORG-29, AC-APR-02,
  AC-APR-03, AC-APR-05, AC-APR-06, AC-APR-07

## Контекст

Закупівля — заголовок і рядки (AC-FRM-07). Вимоги PM кажуть, що подання в чужий відділ, недозволеного типу чи без
рядків не відбувається «зокрема в обхід сторінок застосунку» (AC-FRM-02, AC-FRM-04, AC-FRM-06), а схвалювач не змінює
статус власної заявки «напряму» (AC-APR-05). Data API Supabase відкритий браузеру з токеном користувача, а в
supabase-js немає транзакцій: кожен запит — окрема транзакція. Перевірка в server action і два окремі `insert`
(заголовок, потім рядки) лишають і обхід через Data API, і заявку без рядків, якщо другий запит не вдався.

## Рішення

- `public.purchases` і `public.purchase_lines`: `authenticated` має лише `select` (RLS: автор, схвалювач відділу,
  `admin`, лише активний). Жодних `insert` / `update` / `delete` для користувачів.
- Подання — `submit_purchase(p_department_id, p_purchase_type, p_lines jsonb)`; рішення (задача 3.1) —
  `decide_purchase(p_purchase_id, p_decision, p_reason)`. Кожна — `private.*` (`security definer`,
  `set search_path = ''`) з усіма перевірками й записом в одній транзакції та тонка обгортка `public.*`
  (`security invoker`) для `supabase.rpc`. `execute` — лише `authenticated`.
- Коди винятків (`FORBIDDEN`, `NO_LINES`, далі `NOT_PENDING`, `REASON_REQUIRED`) server action показує текстами PM
  з `MESSAGES`. Server action спершу перевіряє ті самі правила доменною функцією (`src/lib/purchases/`), щоб показати
  повідомлення без запиту до бази; функція бази — друга лінія захисту.
- Кількість чи ціну рядка, які не приводяться до типу колонки, `submit_purchase` перехоплює
  (`invalid_text_representation`, `numeric_value_out_of_range`) і повертає `INVALID_LINE` — загальне повідомлення
  у формі замість помилки бази (зауваження CodeRabbit у kdeineko-tech/school-purchasing#20). Тексту PM для цього
  випадку немає: межі значень — наступний зріз.

## Розглянуті варіанти

- `insert` з RLS `with check` — перевіряє заголовок, але не «хоча б один рядок» (заголовок і рядки — різні запити) і
  дозволяє будь-яку зміну статусу, яку пропустить політика `update`; правило «не власна заявка» довелося б дублювати
  в кількох політиках.
- Перевірка лише в server action — Data API лишається відкритим для прямих запитів (AC-FRM-02, AC-FRM-04, AC-APR-05).
- Ключ `service_role` у server action — обходить RLS для всіх запитів; ключ на сервері Vercel шаблон забороняє.

## Наслідки

- Обхід сторінок дає ту саму відмову, що й форма; заявка без рядків не з'являється навіть при збої мережі.
- Нові поля чи правила (Q8, ValiaBihun/2026-quitcode-dream-team#60; суми й межі — наступний зріз) — новою міграцією
  з `create or replace function`, а не правкою наявної.
- Тести застосунку не бачать SQL: правила функцій перевіряємо на локальній одноразовій базі (`supabase db start`) і
  вручну на проді.
